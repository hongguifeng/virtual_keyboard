# ADR-006：MVP 以普通用户权限运行

状态：已采用（Accepted）

日期：2026-09-06

关联：规格 §3.3、FR-INP-006、NFR-SEC-001、AC-010；方案设计 ADR-006、§12.6、§15.4；任务 T4.6、T7.5、T8.5

## 背景

UIPI（User Interface Privilege Isolation）会阻止低完整性进程向高完整性窗口发送输入。候选策略包括：自动提权 / 请求管理员 / 绕过 UIPI（调试权限、UI Automation 强制输入等）。这些方向均与 NFR-SEC-001（默认普通用户权限、不绕过 UIPI、不操作安全桌面）冲突，或扩大安全攻击面。

## 决策

- MVP **以普通用户权限运行**，不请求管理员、不自提权、不要求 UAC 确认（NFR-SEC-001、AC-010）。
- **不绕过 UIPI**；UIA 仅用于发现/分类/验证，不作为输入路径（方案设计 ADR-006）。
- 向更高完整性窗口输入失败时，失败必须可诊断且不自动提升权限（AC-010）：在键盘状态区域给出简短提示“目标窗口权限高于本程序，输入被系统拒绝（UIPI）”，并按方案设计 §12.6 记录不含输入内容的诊断事件（FR-INP-006）。
- 系统输入桌面（UAC 弹窗、Win+L 锁屏、登录桌面等）属于明确不承诺的场景，不支持绕过（规格 §3.3、NFR-SEC-001）。
- 诊断信息不得包含用户输入内容或按键字符化结果（FR-INP-006、§12.6）；密码目标不得记录 AutomationElement Name/Value（§15.4）。

## 后果

- 优点：无 UAC 噪声、无提权供应链面；高完整性目标失败是明确受控边界而非静默丢失（方案设计 §15.4）。
- 约束：从普通权限向管理员权限（高完整性）窗口注入输入属于明确不承诺范围（规格 §3.3），需在用户文档说明；普通 UWP 应用通常为普通完整性进程，仍须按常规目标校验流程处理，不得笼统视为高完整性；后续如需支持管理员窗口，必须单独评审 `uiAccess`、代码签名与可信安装目录（规格 §3.3、NFR-SEC-001），走独立 ADR 和安全评审。
